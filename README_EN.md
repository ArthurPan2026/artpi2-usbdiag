# ART-Pi2 USB Enumeration Visualizer and Descriptor Rule Checker

> 中文版：[README.md](README.md)

Most hosts report only whether a Universal Serial Bus (USB) device was recognized or failed.
ART-Pi2 makes enumeration of a real human interface device (HID) observable on the board.
It records host requests, device responses, and descriptors so you can inspect how interfaces appeared and which bytes support a rule result.

![ART-Pi2 board and LCD in operation](docs/competition/artpi2-overview.jpg)

*The LCD shows a completed HID enumeration snapshot.*

## Value and use cases

ART-Pi2 is for people learning USB, embedded developers working on USB Host support, and engineers who review HID enumeration results.
It records the requests, responses, and descriptors observed by the Host, helping explain the device-recognition result.

| Use case | What ART-Pi2 helps you do |
|---|---|
| Teach USB enumeration | Follow an eight-stage timeline of host requests and device responses, then complete four evidence-check tasks |
| Integrate or inspect HID devices | Check interfaces, endpoints, descriptor completeness, and Host class-driver binding |
| Debug rules and review results | Follow twelve rule results from expected and observed values to source events and raw bytes |
| Read and share results | Preview, download, or print a Chinese PDF generated by the board; export the complete evidence JSON for deeper review |

The teaching and engineering views use the same session snapshot published by the board.
Firmware and host-side tests also use the same C99 rule core, which keeps their rule behavior consistent.
The core can be built on a host computer. It has no RT-Thread, USB controller, LVGL, or network-stack dependency, and performs no dynamic allocation.

## Reusable components and community work

The USB enumeration rules, Wi-Fi profile manager, and watchdog crash-logging core are independently buildable C99 components used by ART-Pi2. The project includes their source, RT-Thread integration points, and host-side checks.

- [usb_enum_diag](packages/usb_enum_diag/README.md)
- [wifi_profile_manager](packages/wifi_profile_manager/README.md)
- [watchdog_crashlog](packages/watchdog_crashlog/README.md)

These packages are currently distributed with this project and have not been published in the RT-Thread package index. Local upstream patch candidates are not described as submitted or merged contributions.

## Quick start

To view a board that is already flashed, prepare the ART-Pi2, a real HID device, and a computer with a browser on the same local network.
Pair the board with the 正点原子 (ALIENTEK) ATK-MD0430R-800480 4.3-inch RGB LCD module (800 × 480).
Use a Windows 10/11 x64 computer to build firmware. Flashing also requires an ST-Link.

### 1. Choose an image or build firmware

To try the project, use the stable Release images for Boot (the bootloader) and Appli (the application firmware) included in the competition package.
To build firmware, open `ArtPi2Studio.exe` in the package or development-tree root, select `Release` or `Debug`, and click “构建” (Build).

Building does not flash the board. After a successful build, Studio displays the image paths, sizes, and SHA-256 values, then selects the new images for that profile in the current session.
Both the development tree and package can build Debug and Release. The prebuilt stable images in the package are Release.

At startup, Studio verifies the bundled STM32CubeProgrammer 2.23.0 and scans for ST-Link probes.
Probe scanning does not connect to or reset the board. CMake, Ninja, and GNU Arm GCC are checked on demand when you build.

The build defaults to the bundled CMake, Ninja, and GNU Arm GCC. If their package copies have not been extracted, Studio checks disk space and verifies and extracts them automatically on the first build.
You can choose local tools in “工具设置” (Tool Settings) or use the documented environment variables. CMake 3.22 or newer is required; Ninja and GNU Arm GCC are checked for successful execution and target compatibility. STM32CubeProgrammer is checked for the CLI features and read-only probe listing used by Studio, so a local version does not have to match bundled 2.23.0.
The normal GUI workflow does not require PowerShell, Node.js, or a machine-wide .NET Runtime. See the [build and run guide](docs/competition/reproducibility.md) for tool versions, build directories, and advanced settings.

### 2. Flash Boot and Appli for first deployment

Connect the ST-Link and review the target and selected images in the “刷写” (Flash) panel.
Studio selects a single detected probe automatically.

If no flash choices have been saved for the current project and profile, the first-deployment defaults select the bundled stable Release images, include Boot and Appli, and leave read-back verification off.
Click “恢复首次部署默认” (Restore first-deployment defaults) to restore these choices. If `ARTPI2_STLINK_SERIAL` is set, Studio prefers the matching probe; otherwise, choose a probe by serial number when several are connected.
Before flashing, review the target, image source and path, address, and SHA-256 in the confirmation dialog.

Boot is written to internal Flash at `0x08000000`.
Appli is written to the external Flash mapping at `0x70000000` and executes in place (XIP).
A normal flash erases only the sectors covered by the images and preserves Wi-Fi configuration and watchdog history. You can enable read-back verification when needed.

“烧录前完整擦除 Flash” (Full Flash erase before programming) is off by default.
If enabled, Studio erases the microcontroller's internal Flash and the entire 64 MiB XSPI2 external Flash before writing Boot and Appli.
This clears Wi-Fi configuration, watchdog history, and other data on external Flash. Configure Wi-Fi again afterward. Most first-use deployments do not need a full erase.

If Windows reports an ST-Link driver problem, Studio shows “安装驱动” (Install Driver).
Confirm the Windows User Account Control (UAC) prompt to install the driver. Studio does not install drivers at startup.

### 3. Connect the board to Wi-Fi

On first boot, or after a full erase, open “设置 → Wi-Fi” (Settings → Wi-Fi) on the LCD. Scan for and connect to a 2.4 GHz network.
Wait for the Wi-Fi page to show “已连接” and an IP address. Connect the computer to the same local area network (LAN); you can also find the IP in the router's client list.

### 4. Connect an HID device and inspect it

Connect a real HID device to the ART-Pi2 USB Host port. Open `http://<board-ip>/` in a browser.
The board's USB Host Type-C CC resistor configuration can prevent some direct USB-C connections from enumerating HID devices. We strongly recommend a USB-C-to-USB-A adapter for this connection.
The default “HID 接入” (HID Access) view shows interfaces, endpoints, driver binding, and descriptor completeness observed by the USB Host.

Open “教学导览” (Teaching Guide) to follow the eight-stage timeline.
Open “研发核验” (Engineering Verification) to inspect a rule, compare expected and observed values, and follow its source event to raw bytes. After connecting a different device, refresh the topology to view its new USB generation.

### 5. Preview a PDF or export complete evidence

Click “生成并预览 PDF” (Generate and Preview PDF) to open the report generated by the board.
Use the browser PDF toolbar to download or print it. The PDF masks serial numbers by default and omits raw transfer payloads, so it is intended for reading and sharing.

Click “导出完整证据” (Export Complete Evidence) to review the captured data.
JavaScript Object Notation (JSON) retains events and raw bytes captured by the firmware. Check device information before sharing it.
Snapshot identifiers and CRCs detect inconsistent or corrupted data; they do not provide encryption or authentication.

See the [user guide](docs/competition/user-guide.md) for the full page workflow and the [functional validation checklist](docs/competition/functional-validation.md) for post-flash checks.

## How one enumeration becomes evidence

1. The CherryUSB Host adapter observes control transfers and device responses from a real HID device, then places events in a bounded queue.
2. An RT-Thread analysis thread reads the events and calls the shared C99 rule core to produce findings and references to source events and bytes.
3. The board publishes a session snapshot with an identifier. Paged reads remain on the same snapshot, and CRCs detect corruption in returned content.
4. The LCD and Web page display this session. After enumeration succeeds and the evidence snapshot and USB topology are ready, the board prepares a PDF. The complete evidence JSON retains captured events and raw bytes.

[![ART-Pi2 evidence flow from HID connection to export](docs/competition/evidence-flow.svg)](docs/competition/evidence-flow.svg)

*Open the image to zoom in. Editable source: [evidence-flow.drawio](docs/competition/evidence-flow.drawio).*

Live USB topology is read separately and has its own device-generation number. It is outside the frozen snapshot's CRC coverage. When preparing a PDF, the board reads topology separately and checks its generation, identity, and interface/endpoint counts; if the checks fail, the report marks the topology as unavailable and excludes the inconsistent data. An attached topology appendix does not by itself prove that every descriptor was captured. Check the completeness status in the Web view.

## Hardware and software framework

[![ART-Pi2 USB enumeration checker hardware connections](docs/competition/hardware-connection.svg)](docs/competition/hardware-connection.svg)

*A real HID device connects to the board's USB Host port. The LCD shows results, and a browser on the same LAN opens the Web view. A development computer connects through ST-Link. Open the image to zoom in; editable source: [hardware-connection.drawio](docs/competition/hardware-connection.drawio).*

| Layer | Components | Responsibility |
|---|---|---|
| Target hardware | ART-Pi2, STM32H7R7, USB Host, 800 × 480 LCD, CYW43438 | Capture, analyze, and present real HID enumeration on the board |
| Startup and peripherals | RT-Thread 5.3.0, STM32CubeMX, Hardware Abstraction Layer (HAL), Boot, and Appli | Initialize clocks, pins, and peripherals and connect RT-Thread drivers |
| USB capture | CherryUSB 1.5.2 Host and project observation adapter | Record enumeration control transfers, responses, and descriptors |
| Evidence and rules | Bounded event queue, session snapshot, C99 `usb_enum_diag` core | Produce rule findings and references to source events and bytes |
| Network service | Infineon Wi-Fi Host Driver (WHD) 3.3.3.26314, Mongoose 7.23 | Serve the Web view, live topology, and evidence exports over the LAN |
| LCD and reports | LVGL 9.6.0, NemaGFX M7 1.4.17, libHaru 2.4.6 | Display diagnostics and generate a Chinese PDF |

Appli executes in place (XIP) from external XSPI at mapped address `0x70000000`. Routine Appli updates do not write the separate internal Flash region used for Wi-Fi configuration. See [`dependencies/third_party.lock`](dependencies/third_party.lock) for locked dependency versions and hashes.

## Results, privacy, and licenses

- The timeline records the order observed by Host software. It does not measure electrical waveforms or bus timing with a USB protocol analyzer.
- Host class-driver binding does not verify HID input-report transfers. `PASS` means that the corresponding rule passed for the current captured evidence; it is not complete USB compliance certification.
- The complete evidence JSON is not a USB bus-level trace. The engineering view can reveal serial numbers, and JSON retains values captured by the firmware. Review device information and raw bytes before sharing.
- Watchdog fault records help with maintenance, but they are not full RAM dumps and may not contain registers from the exact moment of a CPU hang. See [`Tools/watchdog/inspect_watchdog_faults.ps1`](Tools/watchdog/inspect_watchdog_faults.ps1) to read the records.

The root [`LICENSE`](LICENSE) applies only to project-authored code. RT-Thread, CherryUSB, LVGL, Mongoose, Infineon WHD, libHaru, fonts, radio resources, and board tools retain their own licenses; see [`THIRD_PARTY_NOTICES.md`](THIRD_PARTY_NOTICES.md).
